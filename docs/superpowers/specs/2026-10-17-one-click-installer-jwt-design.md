# One-Click Installer, Commander Connection, and JWT Backend Contract

Date: 2026-10-17

## Purpose and accepted behavior

Cloudflare Manager has two separate React projects in this repository: a small installer and the management frontend bundled into the Go service image. The installer starts with one Install click. On first installation, that click opens Deploy Commander's approval interface to grant the manager a connection to the reserved Commander resource. After approval, the installer starts the run. A denied approval leaves the manager uninstalled. A later installation reuses the approved connection. The installer keeps the latest run, last durable event, and live event listener; the frontend teardown shows the same event history.

The Go backend owns Cloudflare operations and creates, updates, labels, and deletes Deploy Commander connection records through the authenticated manager API. It creates bucket resource records through that API. The frontend supplies operation data in signed requests and keeps the browser-bound tasks the documented manager API cannot perform: Commander child-interface hosting, one-time S3 secret handoff through manager RPC, manager settings RPC, and resource metadata update/deletion through manager RPC. The last two remain because the current Commander manager API documents resource create/read but no resource update/delete routes. Go remains responsible for deciding when those resource RPC operations are needed and for Cloudflare cleanup that precedes them.

The Cloudflare OAuth client ID is an optional manager database setting. The installer can set it through a secondary settings control; leaving it blank never prevents installation. The frontend displays setup until an ID exists and allows editing later. Both interfaces provide a styled button opening `https://dash.cloudflare.com/?to=/:account/oauth-clients` in a new tab. The ID is public configuration, separate from the JWT signing value. The installer asks for no image, origin, password, or OAuth input to start installation.

Frontend-to-backend application calls use separate POST routes. Each request body is a compact JWT containing the operation data. The frontend signs it with a per-manager random value generated during installation, stored in the manager database, and injected into the Go service by the runner. Go verifies the JWT before using its claims. Cloudflare API operations additionally require the user's Cloudflare OAuth cookie. OAuth callback navigation, static asset delivery, and the runner health check are exceptions to JWT POST requests. The backend receives durable Commander Basic credentials from the approved connection secret through the runner; the runner's own short-lived token is never a backend credential.

## Installer and runner

The installer keeps its Commander bridge, run chronology guards, last-event recovery, and React event-listener lifecycle. The visible installer has a primary Install button, status/event display, and an optional collapsed Cloudflare OAuth client ID setting. The optional setting has a save action and a button opening `https://dash.cloudflare.com/?to=/:account/oauth-clients` with `target="_blank"` and `rel="noopener noreferrer"`. A missing ID is setup still needed, not an install error. Saving an ID uses a bound `databaseQuery` to upsert a deterministic manager settings record; each returned statement status is checked.

The installer discovers the unique reserved Commander manager and resource through the authorized interface. It uses the manager UUID for `wire.startInterface` and the resource UUID for the eventual service connection reference. It looks for an existing connection whose manager is this Cloudflare manager and whose resource is the reserved Commander resource. Ambiguous or mismatched records fail clearly. When none exists, it generates a high-entropy manager password with browser Web Crypto and starts the Commander child interface with `action: "create-connection"` and `metadata.createUser.password`. A human approves or denies it. The password travels only in the secure child request and is discarded after approval. The installer verifies the returned connection ID, manager, and resource, then confirms through `getSecretKeys("connection", id)` that Commander stored `COMMANDER_PASSWORD`. The approval result does not carry the password. An existing connection is reused only if its manager, resource, API metadata, and password secret key validate. A missing key is an actionable recovery error, not a reason to create a duplicate connection. A denied or failed approval does not start a run. The parent/child host flow needs staging verification because the Commander integration guide documents forwarding limitations.

The installer reads `manager_api` from the approved Commander connection metadata and validates its host, port, and TLS fields. It does not ask for or derive a Commander API address from a browser origin. The manager service image has a packaged default. A supported, values-capable runner image is selected and pinned at installer build or publication time. The installer build fails clearly if that runner reference is absent or unpinned; the person clicking Install supplies neither image. Install metadata retains the stable service name, health-gated startup, and redirect. It attaches the service through `{ "type": "Connection", "data": { "resource": "<commander-resource-id>", "connection": "<approved-connection-id>" } }`, letting the runner resolve the live platform descriptor and access before Docker mutation. The old inline `Platform` connection is removed. Service environment includes `MANAGER_ID`, `MANAGER_API`, and `MANAGER_PASSWORD`; the last is the runner reference `[[secret:connection:<approved-connection-id>:COMMANDER_PASSWORD]]`, never a literal run value. Go authenticates to Commander's `/api/v1` manager API with Basic credentials and checks `GET /manager` returns its configured manager. The run does not include `CF_CLIENT_ID`, `PUBLIC_ORIGIN`, or `COMMANDER_ORIGIN`.

The runner metadata opts into `values_version: 1`. A one-time runner-role container using the Go service image executes a new `generate-jwt-secret` command, which uses a cryptographically secure random source to produce at least 256 bits. Its captured stdout value is not streamed to logs. The normal manager service depends on this step and receives the value as `JWT_SECRET` through an interpolated environment field. An idempotent database lifecycle hook writes the same captured value into a deterministic manager database record using a bound value. The hook failure fails installation. The backend and database therefore get the same value from one run; a later successful reinstall creates a new value. The value is never placed literally in the install run metadata, run note, event message, or installer bundle. This requires a runner release that supports connection-secret interpolation, captured variables, and database hooks; the selected pinned runner must be verified against that contract before publishing.

The signing value is deliberately readable through the manager database RPC because the frontend signs JWTs in the browser. The frontend reads it when it starts, imports it with browser Web Crypto, keeps it only in memory, and re-reads it after a reload. Access to that value grants the ability to create fresh JWTs until it changes. Enforcing a short JWT expiration does not revoke access to the signing value. This is the selected trust model. The value is separate from Cloudflare access tokens and application S3 secrets.

## JWT request contract

Use the browser Web Crypto HMAC-SHA-256 implementation and Go standard-library HMAC verification; add no JWT library to the installer. Each signed payload contains a manager-specific audience, the exact POST path, the frontend's actual browser origin, `iat`, `exp`, and a route-specific `data` object. The frontend creates a fresh token for each request. Go fixes the accepted algorithm to HS256, rejects unknown or malformed headers, checks the signature in constant time, enforces a short maximum token lifetime of 60 seconds and a small clock-skew allowance, matches the path and manager audience to trusted service configuration, checks the request `Origin` against the signed origin, and validates route data before any Cloudflare call. Requests have a strict body-size limit and `Cache-Control: no-store`; tokens and signing values are never logged. The frontend does not persist JWTs or the signing value in browser storage.

Existing account, zone, bucket, domain, credential, session, and Commander record operations each receive a distinct POST path and a typed payload. Read operations also use POST so that their entire operation data is inside the signed JWT body. Go returns the existing JSON result shapes where practical. Missing, expired, invalid, wrong-path, or wrong-origin JWTs fail before business logic. Missing or rejected Cloudflare cookies still produce the existing sign-in experience. The frontend uses manager-scoped RPC for settings, run start/events, child-interface hosting, connection secret handoff, and the resource metadata update/deletion operations absent from the documented manager API.

For a separately hosted frontend, a preflight OPTIONS response may advertise the requested origin and the JWT content type without returning protected data. The actual POST response allows credentials only when the verified JWT origin equals the request `Origin`. The normal deployment serves the frontend and Go API from the same public origin. Embedded OAuth cookies still require browser-compatible HTTPS routing; removing the installer's public-suffix check does not change cookie behavior.

## OAuth and client ID flow

The frontend reads the saved client ID through Commander RPC. Without an ID it renders setup and does not begin Cloudflare sign-in. When starting OAuth, it opens a blank popup on the user click, signs a JWT for `POST /auth/start` containing the saved client ID, the frontend's actual opener origin, and the HTTP(S) origin of the Go API, then sends the JWT with credentials. The backend validates the signed request and accepts the stated Go API origin when it equals the browser `Origin`; this supports same-origin deployments where a reverse proxy rewrites `Host` to an internal service alias. For a separately hosted frontend, the API origin must match the request host. A mismatch is rejected and logged with the API origin, browser origin, and observed hosts, without OAuth credentials or state. The backend creates PKCE state and verifier, sets the existing short-lived `Secure`, `HttpOnly`, host-only state cookie, and returns the Cloudflare authorization URL. The frontend navigates its already-open popup to that URL. The Cloudflare redirect URI remains the Go API public origin plus `/auth/callback`; this exact URI must be registered on the Cloudflare OAuth client.

`GET /auth/callback` accepts the Cloudflare redirect without a manager JWT. Its protected state cookie includes the client ID, redirect URI, opener origin, and PKCE verifier from the start request, so editing the saved ID during a pending login does not change that exchange. The callback validates state, exchanges the code, sets the current secure HttpOnly Cloudflare access cookie, and posts only a completion signal to the validated opener origin. Cloudflare access tokens never enter JWTs, the manager database, or browser JavaScript. The frontend signs its subsequent `POST /api/session` request to check the OAuth cookie. The backend no longer requires client ID or fixed public/Commander origins at process startup; aside from the runner-injected JWT value and manager identity, the frontend supplies operation-specific OAuth information.

## Commander resource and connection lifecycle

Go uses the authenticated manager API to list and create its `cloudflare-r2-bucket` resource records, list visible connections, read details, create connections for an application manager, replace connection metadata, mutate connection labels, delete connections, and query its manager database. It checks each target resource's `manager` equals `MANAGER_ID` and its type is `cloudflare-r2-bucket`, and each target connection is attached to that resource. It never accepts a caller-provided manager identity as ownership proof. The frontend forwards the trusted `getCallingManager()` value for child creation; Go verifies the resulting owner and resource. Manager API authentication, authorization, conflict, and unavailability errors surface as safe workflow failures.

For a new R2 connection, Go creates a pending Deploy Commander record, creates the scoped Cloudflare R2 credential, and returns its two S3 secret values once in a signed, no-store response to the frontend. The frontend calls `setSecret("connection", id, "AWS_ACCESS_KEY_ID", value)` and `setSecret("connection", id, "AWS_SECRET_ACCESS_KEY", value)` through the authorized interface, checks both keys with `getSecretKeys`, then confirms handoff to Go. Only after confirmation does Go mark the connection ready and put `secret_keys: ["AWS_ACCESS_KEY_ID", "AWS_SECRET_ACCESS_KEY"]` into its **live connection metadata**. Pending, revoked, or incompletely handed-off connections do not claim available keys. Secret values never appear in metadata, labels, child results, or run events. On a failed or abandoned handoff, Go revokes the Cloudflare token and removes the pending connection, or records a retryable revoke state if revocation fails. Connection deletion revokes the token before deleting the Commander record, which also removes its stored secrets.

The frontend hosts the child interface specified by `RESOURCE_CONNECTION_MANAGER_GUIDE.md`; Go performs its record and label work through signed operation routes:

- `create-connection` accepts the selected resource and exact group labels (`custom_deployer_group_id`, `custom_deployer_connection_origin=created`), provisions and completes secret handoff, then returns only `{connection:{id,resource,labels}}` after the ready record exists. Failure or cancellation returns a standard failed interface response.
- `link-connection` validates the resource owner, attached connection, requested group, and `origin=imported`. Go adds only the two requested labels, preserving unrelated labels, then returns the authoritative connection identity and labels. It does not issue another Cloudflare token.
- `unlink-connection` validates the same ownership and that this group's imported connection is being unlinked, removes group and origin labels, preserves the connection and unrelated labels, then returns success. It does not revoke the token.
- `delete-connection` accepts the guide's array of IDs, validates each attached resource is owned by this manager and each target is a created group connection, revokes its Cloudflare token, and deletes the record. A failure reports a failed child workflow; completed items remain deleted and retries reconcile remaining items.

Membership is determined by Deploy Commander's live group labels, not a saved ID list. Go preserves unrelated labels and prevents another manager's or another resource's connection from being modified. It never puts credentials or metadata in labels. For multi-step label changes, it writes/removes the group label last/first respectively and verifies the authoritative result; retry logic reconciles partial updates without treating them as success. Corvo connections remain on their separate workflow. Child results never contain configuration or secret values. The installed `@ezenki/deploy-commander-installer-interface` package must be checked against the guide's `@ezenkico` example and actual host contract before publishing; package names alone are not evidence of compatibility.

The current manager API documents no resource PATCH/DELETE. The frontend therefore keeps authorized `updateResource` for primary CDN metadata and `deleteResource` after Go completes required Cloudflare and connection cleanup. Teardown asks Go to revoke all manager-owned R2 connection tokens and delete their Commander connection records while Go is running, then the frontend deletes now-empty R2 resource records with RPC and starts the runner teardown. It checks for active runs, retains the existing runner-image guard, and shows the latest teardown event after reload and on live updates. A failed cleanup leaves the service running for retry; it does not silently remove the service while tokens or records remain.

## Size, failure behavior, and verification

The installer keeps React and React DOM. Remove its `tldts` import and dependency, the public-suffix trie, unused Tailwind plugin/packages, obsolete origin/client-ID build variables, and install form fields. Retain the Deploy Commander interface dependency and React test tooling. The current build is 501.62 kB minified / 186.25 kB gzip; measure the new output and target below 300 kB minified with no 500 kB chunk warning. Do not claim a plain-TypeScript-sized bundle while React DOM remains.

Installer tests cover first approval, denial, reuse, missing Commander password key, connection UUID/address validation, `Connection` runner reference, optional client ID, pinned images, generated-value references and database hook, run guards, latest event after reload, and live event ordering. Frontend and Go tests cover settings setup/editing, the new-tab Cloudflare button, in-memory JWT signing and route binding, OAuth popup/callback/cookies, Commander Basic API ownership, R2 provisioning and rollback, `secret_keys` only after handoff, child create/link/unlink/delete behavior, label preservation and partial failures, wrong-resource rejection, teardown order, and teardown events. Run both project builds and test suites, Go tests and vet, inspect the installer bundle, and perform a Docker image build when Docker is available. A staging run with a pinned values-capable runner and registered Cloudflare OAuth callback is required to verify approval forwarding, connection-secret interpolation, Commander API access, database hook, S3 handoff, group-label discovery, redirect, cookie, and teardown. The documented Commander parent/child host limitation and runner version support are integration gates, not assumptions that unit tests can prove.

This design supersedes the installer fields and fixed-origin OAuth assumptions in the earlier project-split spec. The existing bucket, domain, token revocation, and teardown semantics remain while Go takes responsibility for the documented Commander manager API operations.

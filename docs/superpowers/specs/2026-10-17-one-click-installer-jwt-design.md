# One-Click Installer and JWT Backend Contract

Date: 2026-10-17

## Purpose and accepted behavior

The published installer deploys Cloudflare Manager with one required action: click Install. It stays a separate React, TypeScript, and Vite project. It displays the latest install run, its last structured event, live updates, and recoverable errors. It does not handle Cloudflare OAuth or require an OAuth client ID, browser origin, or image entry before installation. The bundled management frontend remains a separate React project inside the Go service image and owns OAuth setup, normal management, and teardown.

The Cloudflare OAuth client ID is a manager database setting. The installer can set it through an optional, visually secondary settings control; leaving it blank never prevents installation. After installation, the frontend displays a setup state until an ID exists and allows the ID to be changed later. Both interfaces provide a styled button opening the Cloudflare OAuth clients page in a new tab. The frontend and installer use manager-scoped Deploy Commander RPC to read or update this setting. The ID is public configuration; it is not the JWT signing value.

Frontend-to-backend application calls use separate POST routes. Each request body is a compact JWT containing the operation data. The frontend signs it with a per-manager random value generated during installation, stored in the manager database, and injected into the Go service by the runner. Go verifies the JWT before using its claims. Cloudflare API operations additionally require the user's Cloudflare OAuth cookie. OAuth callback navigation, static asset delivery, and the runner health check are exceptions to JWT POST requests.

## Installer and runner

The installer keeps its existing Commander bridge, run chronology guards, last-event recovery, and React event-listener lifecycle. The visible install form is reduced to a primary Install button, status/event display, and an optional collapsed Cloudflare OAuth client ID setting. The optional setting has a save action and a button opening `https://dash.cloudflare.com/?to=/:account/oauth-clients` with `target="_blank"` and `rel="noopener noreferrer"`. A missing ID is presented as setup still needed, not an install error. Saving an ID uses a bound `databaseQuery` to upsert a deterministic manager settings record; each returned statement status is checked.

The manager service image has a packaged default. A supported, values-capable runner image is selected and pinned at installer build or publication time. The installer build fails clearly if that runner reference is absent or unpinned; the person clicking Install supplies neither image. Install metadata retains the stable service name, manager network connection, health-gated startup, and redirect. It no longer includes `CF_CLIENT_ID`, `PUBLIC_ORIGIN`, or `COMMANDER_ORIGIN`.

The runner metadata opts into `values_version: 1`. A one-time runner-role container using the Go service image executes a new `generate-jwt-secret` command, which uses a cryptographically secure random source to produce at least 256 bits. Its captured stdout value is not streamed to logs. The normal manager service depends on this step and receives the value through an interpolated environment field. A database lifecycle hook writes the same captured value into a deterministic manager database record using a bound value. The hook failure fails installation. The backend and database therefore get the same value from one run; a later successful reinstall creates a new value. The value is never placed literally in the install run metadata, run note, event message, or installer bundle. This requires a runner release that supports captured variables, interpolation, and database hooks; the selected pinned runner must be verified against that contract before publishing.

The signing value is deliberately readable through the manager database RPC because the frontend signs JWTs in the browser. The frontend reads it when it starts, imports it with browser Web Crypto, keeps it only in memory, and re-reads it after a reload. Access to that value grants the ability to create fresh JWTs until it changes. Enforcing a short JWT expiration does not revoke access to the signing value. This is the selected trust model. The value is separate from Cloudflare access tokens and application S3 secrets.

## JWT request contract

Use the browser Web Crypto HMAC-SHA-256 implementation and Go standard-library HMAC verification; add no JWT library to the installer. Each signed payload contains a manager-specific audience, the exact POST path, the frontend's actual browser origin, `iat`, `exp`, and a route-specific `data` object. The frontend creates a fresh token for each request. Go fixes the accepted algorithm to HS256, rejects unknown or malformed headers, checks the signature in constant time, enforces a short maximum token lifetime of 60 seconds and a small clock-skew allowance, matches the path and manager audience to trusted service configuration, checks the request `Origin` against the signed origin, and validates route data before any Cloudflare call. Requests have a strict body-size limit and `Cache-Control: no-store`; tokens and signing values are never logged. The frontend does not persist JWTs or the signing value in browser storage.

Existing account, zone, bucket, domain, credential, and session operations each receive a distinct POST path and a typed payload. Read operations also use POST so that their entire operation data is inside the signed JWT body. Go returns the existing JSON result shapes where practical. Missing, expired, invalid, wrong-path, or wrong-origin JWTs fail before business logic. Missing or rejected Cloudflare cookies still produce the existing sign-in experience. The frontend continues to use the manager-scoped RPC caller for Deploy Commander resources, connections, settings, and runs; only Go calls use these JWTs.

For a separately hosted frontend, a preflight OPTIONS response may advertise the requested origin and the JWT content type without returning protected data. The actual POST response allows credentials only when the verified JWT origin equals the request `Origin`. The normal deployment serves the frontend and Go API from the same public origin. Embedded OAuth cookies still require browser-compatible HTTPS routing; removing the installer's public-suffix check does not change cookie behavior.

## OAuth and client ID flow

The frontend reads the saved client ID through Commander RPC. Without an ID it renders setup and does not begin Cloudflare sign-in. When starting OAuth, it opens a blank popup on the user click, signs a JWT for `POST /auth/start` containing the saved client ID, the frontend's actual opener origin, and the HTTPS origin of the Go API, then sends the JWT with credentials. The backend validates the signed request, requires the stated Go API origin to match the request's public host, creates PKCE state and verifier, sets the existing short-lived `Secure`, `HttpOnly`, host-only state cookie, and returns the Cloudflare authorization URL. The frontend navigates its already-open popup to that URL. The Cloudflare redirect URI remains the Go API public origin plus `/auth/callback`; this exact URI must be registered on the Cloudflare OAuth client. The public proxy must preserve the external host needed for this check.

`GET /auth/callback` accepts the Cloudflare redirect without a manager JWT. Its protected state cookie includes the client ID, redirect URI, opener origin, and PKCE verifier from the start request, so editing the saved ID during a pending login does not change that exchange. The callback validates state, exchanges the code, sets the current secure HttpOnly Cloudflare access cookie, and posts only a completion signal to the validated opener origin. Cloudflare access tokens never enter JWTs, the manager database, or browser JavaScript. The frontend signs its subsequent `POST /api/session` request to check the OAuth cookie. The backend no longer requires client ID or fixed public/Commander origins at process startup; aside from the runner-injected JWT value and manager identity, the frontend supplies operation-specific OAuth information.

## Size, failure behavior, and verification

The installer keeps React and React DOM. Remove its `tldts` import and dependency, the public-suffix trie, unused Tailwind plugin/packages, and obsolete origin/client-ID build variables. Retain the Deploy Commander interface dependency and React test tooling. This preserves the existing UI structure while removing the largest unnecessary bundle component. The current build is 501.62 kB minified / 186.25 kB gzip; measure the new output and target below 300 kB minified with no 500 kB chunk warning. Do not claim a plain-TypeScript-sized bundle while React DOM remains.

Installer tests cover one-click installation with no client ID, optional setting writes and error handling, pinned image and values-capable runner metadata, generated-value references and database hook, run guards, latest event after reload, and live event ordering. Frontend tests cover settings setup/editing, the new-tab Cloudflare button, in-memory JWT signing, POST bodies and route binding, OAuth popup behavior, teardown, and existing resource/connection flows. Go tests cover generated value format, JWT signature/algorithm/audience/path/origin/time/body checks, authenticated routes, cookie requirements, dynamic OAuth start and callback, and client-ID changes during an OAuth flow. Run both project builds and test suites, Go tests and vet, inspect the installer bundle, and perform a Docker image build when Docker is available. A staging run with the pinned values-capable runner and a registered Cloudflare OAuth callback is required to verify the database hook, secret handoff, redirect, cookie, and teardown integration.

This design supersedes the installer fields and fixed-origin OAuth assumptions in the earlier project-split spec. The existing bucket, domain, connection, token revocation, and teardown semantics remain in place while their Go transport moves to signed POST routes.
